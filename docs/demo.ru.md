# AttendBack — демонстрация рабочего продукта

Для знакомства без кошелька открыт [учебный обзор RU](https://attendback-three.vercel.app/demo?lang=ru) / [EN](https://attendback-three.vercel.app/demo?lang=en). Он не выполняет платежи и не заменяет запись работающего продукта. Ниже — сценарий настоящего приложения. Для подачи нужны отдельные demo ≤3 минуты и pitch ≤2 минуты; [подробности](plan-audit-2026-10-09.ru.md).

Материал этапа 9. Сейчас демонстрация работает на **localnet с тестовыми токенами**; пользовательских платежей и публичного devnet-релиза ещё нет. Модель подходит организаторам конференций, сообществам, акселераторам и другим площадкам без обязательного внешнего сервиса регистрации.

Короткая формулировка продукта: «AttendBack помогает организатору уменьшать пустые места: гость вносит возвратный залог, получает билет и возвращает залог после посещения. Правила отмены, спора и защитного возврата зафиксированы в Solana».

Это гипотеза продукта, а не доказанное снижение неявок. Пилот должен измерять долю пришедших, конверсию в оплату залога, заполнение освободившихся мест и долю спорных случаев.

## Подготовка локального показа

Запуск описан в [README](../README.md). Должны работать PostgreSQL, localnet, web, worker и recovery. Затем:

```sh
./scripts/pnpmw demo:seed
```

Команда печатает ссылку на новое демонстрационное событие. Web: `http://127.0.0.1:3000`; recovery: `http://127.0.0.1:4173`. Публичные тестовые роли видны только в localnet; браузер подписывает реальные локальные транзакции, а не имитирует изменение баланса.

Для разных ролей используйте отдельные профили/окна браузера. Повторное бронирование одним гостем той же политики после окончательного расчёта не поддержано; для следующего показа создайте новое событие или используйте другую тестовую роль. Перезапуск localnet очищает цепочку, поэтому прежний билет из БД больше не подходит для показа.

## Сценарий показа

| Шаг           | Действие                                                                        | Что показать                                                                                                          |
| ------------- | ------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------- |
| Организатор   | Вход → организация → событие → публикация                                       | Сумма, время отмены, доля удержания, арбитр, защитный срок; неизменяемая опубликованная политика                      |
| Гость         | Событие → согласие с условиями → бронирование → залог                           | Получатель, сеть, mint, комиссия и подпись; активный билет только после finalized                                     |
| Очередь       | Заполнить событие с одним местом; второй гость встаёт в очередь                 | У второго гостя нет списания; ранняя отмена первого приводит к возврату и предложению места по FIFO                   |
| Вход          | Гость показывает QR; сотрудник выбирает событие и сканирует                     | Повторный QR отклоняется; 30 секунд на исправление ошибочного входа, затем worker подтверждает право возврата         |
| Возврат       | Открыть билет и реестр                                                          | Фактический окончательный расчёт с подписью; возврат за посещение сохраняет активный билет                            |
| Спор          | После закрытия входа гость описывает проблему и подписывает спор; арбитр решает | Приватные материалы, фиксированные сроки, refund/удержание по правилам; обычное удержание блокируется открытым спором |
| Отказ backend | Резервная страница, RPC и адрес депозита из билета                              | Чтение цепочки и допустимый возврат без API AttendBack: Refundable, отмена события или наступивший hard_refund_at     |

В обычном seeded-событии вход открыт сразу, а защитные сроки не сокращены для зрителя. Для демонстрации ранней отмены создайте событие с будущим freeCancelUntil. Для спора нужны подходящие сроки; автоматический браузерный тест создаёт отдельное событие с короткими тестовыми окнами и ждёт время Solana. В публичном пилоте выбирать реальные сроки организатора, а не тестовые интервалы.

Уменьшение пустых мест достигается очередью и условиями залога; блокчейн ограничивает расчёт. Сотрудник по-прежнему отвечает за достоверность факта входа, арбитр — за спор, upgrade authority — за обновление программы. Эти границы доверия следует проговорить на демонстрации.

## Записи и проверка

Локальные записи успешных браузерных сценариев находятся в игнорируемом каталоге `.local/demo-video`:

- `organizer.webm` — создание организации/события и публикация из интерфейса.
- `attendance.webm` — экран гостя: залог, билет, QR, ожидание и квитанция возврата. Сотрудник сканирует QR параллельно в другом браузерном контексте; этот экран не входит в запись гостя.

Это необработанные записи автоматизированного показа, без озвучки; они не выдаются за готовый конкурсный ролик или devnet-демо. Пересоздаются тестами `organizer creates…` и `guest deposits…` в `tests/e2e/flows.spec.ts`. Полный прогон:

```sh
PLAYWRIGHT_BROWSERS_PATH=.local/playwright ./scripts/pnpmw test:e2e
```

Актуальные результаты тестов и остающиеся проверки устройств: [сверка 9 октября](plan-audit-2026-10-09.ru.md) и [журнал](progress.ru.md). Камера локально проверяется на QR из видеопотока Chromium; это не физический телефон.

Состояние каждого этапа: [progress.ru.md](progress.ru.md). Техническая схема: [architecture.ru.md](architecture.ru.md). Порядок внешнего выпуска: [devnet-release.ru.md](devnet-release.ru.md).
