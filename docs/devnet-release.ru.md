# AttendBack — пакет devnet-релиза

Этап 9 [утверждённого плана](../hackathon-product-plan/development-plan.ru.md).
Подготовлен локальный кандидат; программа ещё не развёрнута в devnet, публичные сервисы не опубликованы. Основные сценарии проверены на localnet. Mainnet отключён.

## Что зафиксировано

Машиночитаемые значения и время проверки: [release-manifest.json](release-manifest.json). `sourceBaseCommit` — проверенный коммит до добавления этого пакета; точную идентичность бинарника и IDL задают SHA-256. Манифест не утверждает воспроизводимость бинарника на произвольном компиляторе.

| Параметр                  | Значение                                                                           |
| ------------------------- | ---------------------------------------------------------------------------------- |
| Сеть                      | Solana devnet                                                                      |
| Ожидаемый genesis         | `EtWTRABZaYq6iMfeYKouRu166VU2xqa1wcaWoxPkrZBG`                                     |
| Предполагаемый program ID | `6CUM27mNoskjKnCsoywCQz4puZfhpXj5DJWEDZJuiwuV`                                     |
| Тестовый USDC mint        | `4zMMC9srt5Ri5X14GAgXhaHii3GnPAEERYPJgZJDncDU`                                     |
| Token program             | Обычный SPL Token, 6 знаков после запятой                                          |
| Размер SBF                | 265 152 байта                                                                      |
| Роли                      | Booking authority, attester и worker fee payer — три отдельных адреса              |
| Пользовательские роли     | Организатор, гость, сотрудник и назначенный арбитр подключают собственные кошельки |

Mint проверяется через finalized RPC: владелец SPL Token, инициализация и decimals. Program ID соответствует IDL и сгенерированному клиенту; он обозначает адрес будущего развёртывания, а не уже работающую программу devnet. При смене program ID нужно обновить Anchor, пересобрать SBF, IDL, клиент, web и recovery и повторить проверки.

## Стоимость и недостающие параметры

Чтение RPC дало оценку rent для upgradeable loader с резервом программы вдвое больше текущего бинарника:

- Program account: 833 120 lamports.
- ProgramData: 2 694 823 160 lamports.
- Временный buffer: 1 347 810 360 lamports.
- Постоянно выделяется примерно 2,696 тестовых SOL; пиковая потребность с buffer — примерно 4,043 тестовых SOL плюс комиссии. Buffer rent возвращается после успешного deploy. Это оценка, а не результат развёртывания.

Тестовые SOL/USDC не имеют денежной стоимости. Платный RPC, серверы и домены не заказаны. Стоимость хостинга нельзя определить до выбора провайдера и тарифа.

Перед внешним запуском заполнить публичный адрес плательщика deploy, адрес upgrade authority, три адреса сервисных ролей, публичные web/recovery URL, защищённые доступы к PostgreSQL и сервису подписи. Upgrade authority может менять программу; это доверие должно быть показано пользователю. Не публиковать пользовательские seed-фразы, файлы ключей и токены доступа.

## Размещение

Для web/API на Vercel подготовлены [настройки двух проектов и порядок подключения сервисов](vercel.ru.md). Worker и signer сохраняют отдельное размещение.

Минимальная топология для демонстрации:

1. Node 24 web/API с HTTPS и постоянным доступом к PostgreSQL.
2. Отдельный постоянно работающий Node worker с той же БД и RPC. Обычный короткий serverless request не заменяет worker.
3. PostgreSQL 18 с закрытым сетевым доступом, резервными копиями и проверенным восстановлением. Доказательства спора сейчас хранятся в БД.
4. Изолированный сервис `apps/signer` с отдельными booking/attester/payer ключами. Клиент, сервер и локальные проверки реализованы; внешнее размещение и служебные секреты ещё не настроены. [Инструкция signer](signer.ru.md).
5. Статическая сборка `apps/recovery/dist` на независимом HTTPS-хосте. Она должна быть доступна при отказе основного web/API.

Для VPS Next можно слушать на `127.0.0.1:3000` за HTTPS reverse proxy; процессы web/worker запускает менеджер процессов с рестартом и журналами. Для контейнерного хоста задайте соответствующий bind-адрес. Контейнерное размещение пока не проверено. Не копируйте `.local`, локальную БД и тестовые ключи на публичный сервер.

## Контракт сервиса подписи

`packages/server/src/chain.ts` отправляет POST на `SERVICE_SIGNER_URL` с Bearer `SERVICE_SIGNER_TOKEN`:

```json
{
  "role": "booking",
  "cluster": "devnet",
  "program": "6CUM27mNoskjKnCsoywCQz4puZfhpXj5DJWEDZJuiwuV",
  "transactions": ["base64 полной сериализованной транзакции"]
}
```

Ответ — `{"signatures":["base64 подписи Ed25519"]}`, по одной подписи **байтов сообщения** каждой транзакции, в исходном порядке. Допустимые роли: `booking`, `attester`, `payer`. Клиент проверяет каждую подпись по настроенному публичному адресу; сервис не должен менять сообщение или отправлять транзакцию.

Сервер `apps/signer` разбирает и заново собирает транзакцию, проверяет разрешённые инструкции, signer-role, program ID, сеть, допустимые суммы/плательщика, комиссию и симуляцию. Поля `cluster` и `program` из JSON сами по себе не считаются доказательством. Реализованы аутентификация, журнал без секретов и лимиты. Защищённые mount-файлы служебных ключей, HTTPS и изоляцию процесса ещё предстоит настроить и проверить на выбранном хостинге.

## Последовательность выпуска

1. Заполнить конфигурацию по `.env.devnet.example` через секреты выбранного хостинга. `NEXT_PUBLIC_RECOVERY_URL` — публичное значение **во время сборки**, остальные секреты не имеют префикса `NEXT_PUBLIC_`. Web и worker должны получить одинаковые DB/RPC/сервисные роли.
2. Выполнить `./scripts/pnpmw release:check` с этими переменными. Проверка валидирует обязательные параметры, HTTPS, отдельные сервисные адреса и genesis; ничего не подписывает. Она не доказывает работоспособность signer, БД или программы.
3. На проверенном toolchain собрать `anchor build`, выполнить `codegen`, `typecheck`, тесты и обе production-сборки. Сверить `git diff` IDL/клиента. Обновить `release:manifest` (только чтение RPC).
4. Сверить публичный адрес program keypair с program ID, плательщика, upgrade authority, финальные хеши, полномочия и выбранную стоимость размещения. Только после этого выполнить согласованный deploy в devnet. Автоматического deploy-скрипта в этом пакете нет.
5. Проверить executable/loader, authority и выгруженный бинарник программы, записать подпись deploy, programdata, слот и SHA-256 в отдельный протокол фактического релиза. Не подменять текущий статус `not_performed` до проверки.
6. На новой devnet БД выполнить миграции; собрать web с recovery URL, запустить web и worker. Опубликовать recovery независимо. Скрипт `demo:seed` предназначен только для localnet: devnet-событие создаётся через кошелёк организатора.
7. Выдать сервисному fee payer тестовые SOL, гостю — тестовые SOL и USDC. Выполнить живые сценарии из [demo.ru.md](demo.ru.md) с обычным Wallet Standard кошельком и камерой физического телефона по HTTPS. Проверить и v0 fallback, и поддержку выбранного кошелька.
8. Записать адреса, версии, подписи расчётов, браузер/кошелёк/телефон и результат восстановления. Код опубликован в [ernur077sss-art/AttendBack](https://github.com/ernur077sss-art/AttendBack); подтверждение CI и отправка заявки — отдельные действия. Актуальные результаты — в [журнале прогресса](progress.ru.md).

Команды процесса при уже настроенном окружении:

```sh
./scripts/pnpmw install --frozen-lockfile
./scripts/pnpmw release:check
./scripts/pnpmw db:migrate
./scripts/pnpmw build
./scripts/pnpmw recovery:build
./scripts/pnpmw start
# отдельный процесс
./scripts/pnpmw worker
```

Не запускать localnet и `demo:seed` на devnet-хосте. При отказе RPC не освобождать PaymentPending вручную; дождаться сверки finalized состояния. При остановке основного приложения резервный клиент позволяет выполнить разрешённый возврат через RPC. Для восстановления БД нужны реальные backup/restore выбранного хостинга; локальный тест восстановления не заменяет эту настройку.
