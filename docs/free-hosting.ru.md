## Очередь без постоянного сервера

После успешного изменения через API `after()` возобновляет обработчик или запускает новый Workflow. Именованный hook предотвращает одновременную работу нескольких экземпляров. Каждый шаг обрабатывает до пяти записей сверки и до двух заданий. Сохранение подписанной транзакции перед отправкой, блокировки, leases и идемпотентные квитанции остаются в PostgreSQL.

Расписание учитывает очередь, незавершённые транзакции, брони и сроки политики. При активной работе минимальный интервал — 15 секунд; при отсутствии работы Workflow засыпает на сутки, позволяя Neon остановить вычисления. Сроки лишь пробуждают обработчик: допустимость операций по-прежнему определяется часами Solana. После 200 циклов обработчик продолжает работу в новом запуске. Cron `0 3 * * *` защищён отдельным `CRON_SECRET` и служит резервным запуском.

Сразу после отметки посещения действует существующее 30-секундное окно исправления. Облачная обработка добавляет интервалы пробуждения и ожидание finalized. Успешный ответ check-in не означает уже выполненный возврат: интерфейс показывает фактическое состояние расчёта.

## Изоляция подписи

Проект signer собирается командой `pnpm --dir ../.. build:signer`, с `ENABLE_EXPERIMENTAL_COREPACK=1`, Node 24 и Include source files outside Root Directory. `/api/sign` и `/api/health` требуют Bearer-токен. Без него RPC и ключи не инициализируются. В signer нет доступа к PostgreSQL.

Только в Production-переменных **проекта signer**, типа **Sensitive**, хранятся `SERVICE_SIGNER_TOKEN` и `SIGNER_BOOKING_KEY_BASE64`, `SIGNER_ATTESTER_KEY_BASE64`, `SIGNER_PAYER_KEY_BASE64`. Base64 содержит JSON-массив 64 байтов Solana keypair; это кодировка, не шифрование. При холодном запуске адаптер создаёт временные файлы с правами 0600, использует существующую проверку формата/адресов, затем удаляет их. Адреса трёх ролей, devnet RPC и genesis задаются отдельно. Ключи deployer и upgrade authority не загружаются в Vercel.

Web получает тот же токен и только публичные адреса; build guard отвергает приватные переменные signer. Прежняя политика проверяет genesis, программу, mint, конкретную операцию, сумму, получателя, комиссию и симуляцию. Это изоляция по проектам и переменным окружения, а не аппаратный KMS. Ограничитель запросов действует на экземпляр функции.

## Квоты и эксплуатация

Нулевой тариф не означает неограниченную нагрузку. Hobby предназначен для личных некоммерческих проектов; это devnet-прототип для хакатона. При превышении квот сервис может остановиться. Платные планы не подключались. Следить за квотами Vercel Functions, Workflow, Queues и Neon; реальные деньги и коммерческие мероприятия требуют отдельного решения о размещении.

Не запускать постоянный worker одновременно с Workflow без необходимости. Не выдавать preview-веткам production-ключи. Перед публикацией Preview требуется отдельная БД/ветка и набор devnet-ролей: текущая интеграция Neon создала переменные и для Preview, но preview-deployment ещё не выпускался.

Миграции выполняются отдельным шагом, не в build. Приватные ключи, `.env`, `.local`, бинарные артефакты и локальные состояния Workflow не публикуются в Git. Прямые загрузки исходников через Vercel API не настраивают автоматический deployment после Git push; GitHub Login Connection пока отсутствует.

## Проверки и остаток этапа 9

Прошли TypeScript, сборки web/Workflow и signer, 46 модульных/программных/signer-тестов, три новых PostgreSQL-теста расписания, включая сохранение пробуждений для депозитов, не попавших в первый пакет. Сквозной браузерный сценарий «залог → QR → finalized-возврат» прошёл без отдельного worker (1/1, 1,5 минуты со стартом стенда).

Облачный сценарий через HTTPS API прошёл: публикация → залог 1 тестового USDC → QR-токен → автоматический finalized-возврат, билет Active. Остаются обычный кошелёк, физическая камера телефона, публичный recovery-сценарий и дополнительные devnet-проверки неявок/споров. Они не заменяются автоматизированной проверкой API.
