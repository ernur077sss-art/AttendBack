## Что исправлено при этой проверке

1. **Потеря второй квитанции при групповом расчёте.** Solana допускает несколько settlement-инструкций в одной транзакции. Уникальность `ledger.signature` ошибочно запрещала вторую запись. Миграция 006 сохраняет уникальность по регистрации; квитанции и уведомления теперь независимы для каждого депозита. Повторная сверка не дублирует уведомление. В квитанцию записывается слот самой транзакции.
2. **Неверная подпись квитанции.** Упоминание депозита в дополнительных аккаунтах чужого settlement считалось доказательством выплаты. Теперь адрес должен находиться именно в позиции commitment инструкции AttendBack. Тест воспроизвёл ошибку реальной второй транзакцией и проверяет правильную подпись после исправления.
3. **Задержка оплаченных депозитов и задания для отсутствующих залогов.** Освобождённые неоплаченные регистрации исключены из периодической сверки. Ожидающие оплаты записи перемещаются в очередь после проверки; денежные задания создаются только при подтверждённом состоянии депозита. Тест использует 100 освобождённых и 100 ожидающих записей перед оплаченным депозитом.
4. **Ошибка одной брони останавливала worker.** Истечение резерва теперь обрабатывает ошибки по записям, сохраняет занятое место и ошибку для организатора, продолжает остальные задания. Регрессионный тест проверяет доставку независимого уведомления при недоступных данных одного депозита.
5. **Неполный журнал входа.** Раньше сохранялась только последняя отметка и номер версии. Миграция 007 и транзакционные записи сохраняют автора, время, действие и версию каждой новой отметки/коррекции. История доступна сотрудникам своей организации и организатору; арбитр и посторонний пользователь её не получают. Старые действия, совершённые до появления журнала, восстановить задним числом нельзя.
6. **Ошибка полного браузерного прогона.** `afterAll` одного файла закрывал общий пул PostgreSQL, который Playwright повторно использовал в следующем файле. Теперь пул закрывается один раз при завершении worker. Адресные успешные прогоны ранее не выявляли эту ошибку.

Первые три регрессионных теста были запущены до исправления: все три воспроизвели соответствующую ошибку. Дополнительная проверка БД принудительно отклоняет запись квитанции после on-chain расчёта: проекция целиком откатывается, а повторная сверка после снятия сбоя восстанавливает обе квитанции.
