# Изолированный signer для devnet

Продолжение этапа 9: `apps/signer` реализует сервер API, который использует web/worker. Сервис хранит **только отдельные служебные ключи**; пользовательские подписи по-прежнему выполняются кошельком. Внешнее размещение и реальные сервисные ключи ещё не настроены.

## Разрешённые подписи

| Роль     | Допустимое сообщение                                                                         | Плательщик               |
| -------- | -------------------------------------------------------------------------------------------- | ------------------------ |
| booking  | Единственная инструкция `deposit` для существующей политики и обычного SPL mint              | Сам гость                |
| attester | `attest_present` либо `propose_no_show`                                                      | Настроенный worker payer |
| payer    | Та же attestation либо два idempotent создания фиксированных ATA + `settle`/`timeout_refund` | Настроенный worker payer |

Signer читает finalized Event/Policy/Commitment, проверяет владельца, длину, discriminator, PDA, mint, служебные роли, principal, состояние и часы Solana. Он заново собирает разрешённое сообщение и сравнивает **все байты**, включая порядок инструкций, адреса и права аккаунтов. Это отклоняет дополнительные переводы, чужие ATA, лишние аккаунты и расширение полномочий. Проверка genesis привязана к devnet, mint — к тестовому USDC, program ID — к сгенерированному клиенту.

Поддерживаются v0 и v1; ALT и durable nonce в служебном signer не поддержаны. Для v0 допускаются только известные ComputeBudget setters перед основной инструкцией, без дублей. Запрашивается комиссия всего сообщения и выполняется симуляция до подписи. Все элементы пакета проходят проверку до запроса первой подписи. Signer **не отправляет** транзакции.

Лимиты по умолчанию: максимум 4 транзакции в запросе, 24 000 байт JSON, 4 параллельных запроса, 60 запросов в минуту, комиссия до 50 000 lamports за транзакцию, залог до 1 000 тестовых USDC. Последние три параметра настраиваются в ограниченном диапазоне. Лимит суммы — эксплуатационный предел сервиса, он не меняет опубликованную on-chain политику. Счётчик запросов находится в памяти одного процесса и сбрасывается при рестарте; это не устойчивый суточный бюджет. Расход на создание максимум двух ATA оплачивается отдельно от сетевой комиссии и ограничен фиксированными получателями.

## Подготовка и запуск

1. Развернуть проверенную программу в согласованной devnet, затем заполнить `.env.signer.example`. До этого старт сервиса намеренно завершается ошибкой.
2. В выбранном секретном хранилище подготовить **три новые служебные devnet-идентичности**, отдельные от пользовательских и mainnet-кошельков. Публичные адреса должны совпадать с `SIGNER_*_ADDRESS` у web/worker и signer. Публичные localnet seeds для этого непригодны.
3. Доставить секреты через защищённые mount-файлы: три стандартных JSON-массива keypair по 64 байта и случайный API-токен длиной не менее 32 символов. Пример путей — в `.env.signer.example`; файлов в репозитории нет. Каждый файл должен принадлежать пользователю процесса signer, иметь режим `0400` или `0600` и размер не более 4096 байт. Не копировать эти файлы в web/worker, исходный код, образ или Git. В чат их отправлять не нужно.
4. Запустить `./scripts/pnpmw signer` с переменными окружения. Процесс слушает исключительно `127.0.0.1:8787`. `GET /health` подтверждает загрузку ключей; каждая подпись отдельно проверяет сеть и состояние. Backend отправляет тот же API-токен через `SERVICE_SIGNER_TOKEN` на HTTPS `SERVICE_SIGNER_URL`.
5. На том же хосте настроить HTTPS reverse proxy с приватным доступом только для web/worker; добавить IP allowlist или mTLS и отдельный лимит трафика. Внешний `Origin` отклоняется, CORS не разрешён. HTTP-порт signer не должен быть доступен извне. Прокси не должен удалять `Origin` с произвольных браузерных запросов или журналировать Authorization/тело.
6. На Linux доступен шаблон `deploy/attendback-signer.service`: отдельный системный пользователь, файловая система только для чтения, отключённые Linux capabilities. Указать фактический путь Node и проекта. Шаблон ещё не проверен на выбранном VPS; на macOS он не устанавливался.

Web/worker и signer могут читать одинаковый проверенный код, но работают под разными пользователями. Каталог секретов доступен только signer. API-токен даёт web/worker право запрашивать **разрешённые** подписи; компрометация backend всё ещё позволяет злоупотребить бронированием/подтверждением входа в пределах полномочий. Сервис не доказывает физическое присутствие и не читает PostgreSQL. Достоверность check-in и распределение мест остаются ответственностью backend и сотрудников.

При ротации booking/attester нельзя просто заменить адреса у уже опубликованных политик: роли зафиксированы в программе. Для активных событий нужно сохранить прежний сервис до завершения обязательств либо выполнить согласованную отмену/возврат; новые роли используют новые политики. При отказе сервиса кошелёк гостя и независимый recovery сохраняют разрешённые программой способы возврата.

## Проверка

```sh
./scripts/pnpmw typecheck
./scripts/pnpmw test:signer
```

13 тестов проверяют реальные SBF-симуляции в LiteSVM, подписи Ed25519, backend-клиент, HTTP на localhost, фиксированных получателей, неправильные роли, сеть, mint, vault, расширение прав, дополнительные переводы, истёкшие разрешения, предел комиссии, пакет с ошибкой, повторный расчёт, авторизацию и лимиты. В тестах ключи создаются в памяти; genesis и fee quote заменены контролируемыми ответами, live devnet здесь не имитируется как выполненный тест. Адаптер внешнего RPC и инфраструктуру предстоит проверить после размещения программы.

Результат общего локального прогона после добавления signer: 30 тестов проходят. Отдельный запуск signer без конфигурации ожидаемо прекращается до открытия порта. Независимый аудит не проводился; запуск с реальными средствами не поддержан.

При реализации формата подписи сверены установленные типы Kit 8.4 и [официальное описание транзакций Solana](https://solana.com/docs/core/transactions).
