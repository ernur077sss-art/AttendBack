**AttendBack — продукт, архитектура и план реализации**

Версия 3 · 7 октября 2026. Это проектная спецификация, подготовленная через ProofPilot с техническими рекомендациями solana-dev. Код, развёртывание, испытания и партнёрства этим документом не подтверждаются. Развивает выбранный пользователем AttendBack: самостоятельный сервис, собственная регистрация и check-in; без обязательной связи с Luma. Предыдущая версия сохранена в archive/product-plan-attendback-v2-2026-10-07.md.

**1. Как упаковать продукт**

Рабочая формулировка: **AttendBack — возвратные залоги за участие в мероприятиях: понятные условия для гостя, учёт посещений и возвратов для организатора.**

Английская строка: **“Attendance deposits. Clear rules. Automatic refunds.”** Для заявки до готовности реализации: *“We are building AttendBack to help event organizers manage refundable attendance deposits, verify check-ins, and return funds under clear, predefined rules.”*

Покупатель — руководитель мероприятий или программ. Его предполагаемая задача: провести событие с ограниченными местами и разобраться с возвратными залогами без ручного сопоставления списков и переводов. Гость должен понимать сумму, условия, срок и состояние возврата. Сотруднику на входе нужен быстрый ответ по конкретному билету.

Начальный сегмент: регулярные воркшопы, закрытые встречи и образовательные сессии, где организатор уже использует залог или согласен его проверить. Для крупного хаба начинать с отдельной сессии. Астана Хаб — потенциальный тип заказчика из обсуждения, не подтверждённый партнёр. Заявления «подходит любой конференции» и «снижает неявки» пока не доказаны.

Основное обещание первого прототипа — законченный и проверяемый процесс возврата. Уменьшение неявок — отдельная гипотеза. Если организатору не нужны залоги, простая регистрация через AttendBack сама по себе не даёт убедительной причины перейти.

Предлагаемая структура лендинга:
- Первый экран: обещание продукта, схема «Залог → посещение → возврат», кнопка «Создать тестовое событие».
- Пример кабинета с посещениями, возвратами и исключениями.
- Условия для гостя: что вносится, кто подтверждает посещение, когда возвращается, что происходит при отмене.
- Приглашение организатору провести пилот. До действующего продукта явно обозначить прототип/devnet.

Главные метрики кабинета: внесённые залоги, подтверждённые посещения, завершённые возвраты, случаи с ошибкой. Сумма залогов не показывается как выручка организатора.

**2. Один сквозной сценарий**

Для демонстрации: вымышленный «Community Workshop», один организатор, один сотрудник на входе, три тестовых участника. Это размер теста, не подтверждённая вместимость продукта.

1. Организатор задаёт событие, сумму залога и сроки; публикует условия.
2. Гость открывает ссылку AttendBack, принимает условия, связывает кошелёк и вносит тестовые токены.
3. После проверки внесения средств получает QR-билет.
4. Авторизованный сотрудник сканирует билет.
5. После окна исправления система подтверждает посещение и инициирует возврат.
6. Гость видит квитанцию; организатор — итог и оставшиеся исключения.

Предлагаемые пять экранов:

| Экран | Содержимое и основной результат |
|---|---|
| Настройка события | Название, даты, залог, правила, публикация |
| Страница события | Условия до оплаты; регистрация и связь кошелька |
| Билет участника | Сумма, QR, состояние, срок возврата, квитанция |
| Сканер сотрудника | Камера/ручной ввод, результат, причина отказа |
| Реестр организатора | Посещения, возвраты, фильтр ошибок и повторная проверка |

Состояния интерфейса: «Ожидает подписи», «Проверяем внесение», «Билет готов», «Посещение подтверждено», «Возврат обрабатывается», «Возвращено», «Нужна проверка». Ошибку RPC нельзя показывать как успешную оплату или окончательную потерю средств.

В MVP вход по подписи кошелька с одноразовым challenge, доменом и сроком; роли организатора/сотрудника назначены заранее. Для закрытого теста контакт и имя сверяются вручную. Это упрощает запуск без отдельного поставщика SMS/email, но не является автоматической проверкой личности. Для публичного пилота добавить проверку контакта и оценить её влияние на конверсию.

**3. Архитектура**

~~~mermaid

 U["Гость: регистрация, депозит, билет"] --> A["Next.js UI + API"]
 S["Сотрудник: QR-сканер"] --> A
 O["Организатор: событие и реестр"] --> A
 A --> D["PostgreSQL: регистрации, отметки, задания"]
 D --> W["Worker: проверки и повторные попытки"]
 U --> P["Solana / Anchor: депозит и правила возврата"]
 W --> P
 P --> W
 W --> D
 F["Резервная страница участника"] --> P
 X["Будущие внешние источники посещений"] -.-> A
~~~

Один репозиторий: web-приложение с API, worker, программа Anchor, сгенерированный клиент и тесты. PostgreSQL служит также очередью заданий. Для этого объёма предлагаю обойтись без Redis и микросервисов.

Предлагаемый клиент: TypeScript, Next.js, @solana/kit, @solana/react и Wallet Standard. Официальная документация описывает Kit и React bindings для такой работы; совместимые версии кошельков и пакетов нужно проверить при сборке. [Solana Frontend](https://solana.com/docs/frontend), проверено 7 октября 2026.

Размещение после реализации: web/API на доступном команде хостинге, PostgreSQL и долгоживущий worker. Если web работает в короткоживущих serverless-функциях, обработчик очереди всё равно должен запускаться отдельно либо через надёжный планировщик. Выбор тарифа и доступность ресурсов пока не установлены.

База хранит контакты и операционные записи. Программа хранит условия расчёта и движение залога. Кэш БД не считается доказательством перевода; он сверяется с состоянием программы.

**4. Модель данных**

| Сущность | Минимальные поля и правило |
|---|---|
| Organization, StaffMembership | Организация, wallet пользователя, роль, доступные события |
| Event | Организация, on-chain адрес, сроки, mint, сумма, версия/хэш условий, статус |
| Registration | Event, wallet участника, контакт по необходимости, принятое правило; unique(event, wallet) |
| Ticket | Registration, хэш случайного QR-секрета, состояние |
| CheckInEvent | Registration, действие, автор, server time, revision, request ID; журнал без перезаписи |
| RefundJob | Deposit, операция, попытки, next_run, lease, последняя ошибка; unique(deposit, operation) |
| ChainOperation | Deposit, операция, подпись транзакции, blockhash/срок действия, статус проверки |
| AuditEntry | Кто, что и когда изменил; без секретов билетов/подписывающих ключей |

Физический лимит мест в первом закрытом тесте контролирует организатор. Продажа последнего места, временные резервы, список ожидания и защита публичной регистрации от массовых заявок — следующая итерация; счётчик в UI не выдаётся за гарантию вместимости.

QR содержит случайный непрозрачный секрет. API не принимает имя или кошелёк из QR как доверенные данные. Проверяет полномочия сотрудника, событие, билет и наличие депозита. Секрет не помещается в журналы. Дубликат запроса возвращает прежний результат. Передача скриншота другому человеку остаётся возможной: при необходимости сотрудник сверяет имя по правилам мероприятия.

**5. Предлагаемый API**

Это проект интерфейса собственного backend, а не уже реализованные маршруты.

| Маршрут | Назначение и доступ |
|---|---|
| POST /auth/challenge, /auth/verify | Одноразовый вход подписью; защита от повтора |
| POST /events | Создание события; только организатор |
| GET /events/:slug | Публичные условия, без персональных данных |
| POST /events/:id/registrations | Связать текущий кошелёк с регистрацией и условиями |
| POST /registrations/:id/deposit-intent | Построить неподписанную транзакцию для владельца |
| GET /registrations/:id/status | Состояние билета и расчёта; владелец либо уполномоченный сотрудник |
| POST /events/:id/check-ins | Проверка билета; сотрудник данного события, Idempotency-Key |
| POST /check-ins/:id/correction | Исправление в разрешённое окно, с проверкой revision |
| GET /events/:id/reconciliation | Реестр своего организатора |
| POST /deposits/:id/reconcile | Повторно проверить сеть и поставить допустимое задание |

Сервер проверяет доступ к объекту в каждом запросе. Идентификатор события из URL сам по себе не даёт доступа. Отдельный вызов «пометить возврат успешным» из браузера не допускается.

**6. Программа Solana и возврат**

На уровне события фиксируются authority, attester, выбранный mint обычного SPL Token, сумма, конец регистрации, окно посещения, жёсткий срок возврата и хэш условий. Для хакатона — тестовый токен devnet, без Token-2022 extensions и без заявления, что это реальные USDC.

**Получатель фиксируется отдельно в каждом Deposit:** кошелёк участника, подписавшего внесение средств. Он не является общим получателем Event. Предлагаемый адрес Deposit выводится из event + wallet; повторное внесение для этой пары запрещено в MVP. Хранилище токенов отдельное для каждого депозита, под управлением программы через PDA. Ограничения seeds/bump проверяют правильность PDA; нужны также проверки владельца аккаунта, mint, получателя, подписи и состояния. [Anchor PDA](https://www.anchor-lang.com/docs/basics/pda), проверено 7 октября 2026.

Правила неизменяемы после создания on-chain события; изменение формы требует нового события. Время проверяется по часам сети. Хэш связывает правила с опубликованным текстом, но не доказывает их качество: копия условий доступна участнику до оплаты.

| Операция | Кто инициирует | Условие и эффект |
|---|---|---|
| create_event | Organizer authority | Фиксирует правила; проверяет порядок сроков |
| deposit | Подписавший участник | До конца регистрации, событие активно; переводит точную сумму в vault, создаёт Funded |
| attest_attendance | Назначенный attester | Депозит Funded, допустимое окно; переводит в Eligible |
| refund | Любой отправитель | Только Eligible; перевод строго исходному получателю, состояние Refunded |
| cancel_event | Organizer authority | Запрещает новые депозиты и открывает возвраты |
| timeout_refund | Любой отправитель | Событие отменено или истёк hard_refund_at; Funded/Eligible → Refunded тому же получателю |

Перевод и смена состояния выполняются атомарно. Закрытие записи не должно позволять создать тот же депозит повторно: финальный маркер сохраняется как минимум до окончания всех сроков события. Подмена получателя и повторный вывод должны отклоняться программой.

В UI возврат начинается автоматически через worker. Сама программа по таймеру не запускается: нужна транзакция worker или другого отправителя. Резервная статическая страница с отдельным размещением читает депозит через RPC и строит разрешённый возврат без backend и подписи организатора; нужна доступная сеть/RPC и оплата комиссии отправителем.

Контактные данные не публикуются в сети. Сервисный attester подтверждает посещение; он и организатор остаются доверенными. Это не независимое доказательство присутствия. Upgrade authority и последствия обновления программы явно документируются; без дополнительных мер нельзя обещать полную независимость условий от владельца обновлений.

В хакатонной версии неявка не вызывает штраф: неподтверждённый залог возвращается по жёсткому сроку. Это тест автоматизации и прозрачности возврата, а не доказательство финансовой мотивации прийти. Удержание за неявку можно исследовать после пилота: заранее согласованные условия, споры, ошибки check-in и отмена должны быть решены до реальных средств.

**7. Как переживать сбои**

Запись check-in и задания outbox создаются одной транзакцией БД. Worker получает задание с lease, повторно проверяет актуальную отметку и ожидает окно исправления. Для демо предлагается 30 секунд, явно обозначенные как тестовая настройка.

Исправление и переход в состояние «готово к attest» используют блокировку одной записи. После этого исправление не считается гарантированным откатом: интерфейс блокирует обычную отмену и предлагает зарегистрировать исключение. После on-chain Eligible право возврата уже выдано. Такой порядок устраняет обещание «успеем отменить», когда транзакция уже отправляется.

Worker сохраняет подписанную операцию и её подпись до отправки. При неопределённом ответе RPC сначала ищет результат и читает депозит; пока транзакция действительна, повторяет ту же операцию. Новую собирает после проверки срока действия и актуального состояния. Ограниченная повторная обработка уходит в реестр ошибок. On-chain проверки защищают от двойной выплаты даже при двух worker.

Билет выдаётся после проверки finalized состояния депозита; до этого — «проверяем внесение». Возврат считается завершённым после finalized состояния и соответствующей операции. Баланс кошелька сам по себе не используется как доказательство конкретного платежа.

Отдельная сверка восстанавливает отставший реестр после рестарта. Отмена события открывает возвраты, но не означает, что все выплаты уже произошли: они выполняются по депозитам и отображаются отдельно.

**8. Что реализовать до подачи**

Обязательный результат: депозит → билет → собственный check-in → возврат, плюс повторная отметка без повторной выплаты, отмена и возврат по сроку. Одна организация, заранее назначенные роли, три тестовых гостя, пять простых экранов. Сначала местные тесты программы, затем согласованный devnet-прогон.

Внешние адаптеры, импорт списков, платежи картой/в тенге, embedded wallet, рассылки, SSO, несколько зон, реферальные механики и сложная аналитика — последующие этапы. Унифицированный будущий адаптер должен передавать event, attendee, source, message_id, revision, occurred_at и действие; право доверять источнику проверяется отдельно. Luma лишь один возможный источник.

Для массовой аудитории главный риск — внесение залога и кошелёк могут снижать регистрацию. После хакатона проверить понятный вход и платёжный канал. Банковский эквайринг требует отдельного процесса расчёта и возврата; перевод в тенге не становится SPL-депозитом автоматически.

Ресурсы: технический исполнитель для full-stack, исполнитель с опытом Solana, организатор для проверки; роли могут совмещаться, но задачи тогда идут последовательно. Нужны Node/Rust/Anchor, кошелёк, RPC, PostgreSQL, запуск worker и запись экрана. Доступность и совместимость окружения, состав команды и бюджет пока неизвестны. Расходы включают хостинг, БД/RPC, комиссии и создание аккаунтов, а позднее сообщения/платёжного провайдера; точная сумма не установлена. Автоматическая покупка услуг планом не предусмотрена.

Предыдущие 28 человеко-часов — условный бюджет попытки, не проверенная оценка всего этого объёма. Ниже контрольные рубежи для двух технических исполнителей с готовым окружением; это не гарантия успеть с нуля:

| Срок | Работа и владелец | Проверяемый результат |

Если цикл не готов и после сокращения, обозначить неполный прототип; не подменять экраном успешного возврата несуществующую транзакцию. При одном разработчике полноценный объём с нуля особенно неопределён; обещать результат за прежние 28 часов нельзя.

**9. Проверка ценности и критерии готовности**

Техническая приёмка: ошибочный mint/получатель/сотрудник/чужой QR отклоняются; повторная отметка и параллельные задания дают одну выплату; после потери ответа RPC и рестарта итог восстанавливается; отмена и таймаут доступны; резервная страница работает при выключенном backend. Автоматизированные тесты программы дополнить одним сквозным тестом UI. На момент документа проверки не запускались.

Малый тест: один организатор и три приглашённых участника. Предлагаемый порог для перехода к более широкому пилоту: все три завершают сценарий без вмешательства разработчика, правильно объясняют условия возврата; нет неверных/двойных выплат; организатор закрывает реестр без ручного перевода и согласен повторить на конкретном событии. Это исследовательский порог, не статистическое доказательство спроса.

Измерять время регистрации/возврата, число подсказок и ручных исправлений. Если есть сопоставимый прежний процесс, засечь его отдельно; без исходного замера нельзя заявлять процент экономии. Если порог не выполнен — исправить конкретное препятствие и повторить ограниченный тест; при нехватке времени записать непрохождение. Если тест не состоялся — оставить статус «не проверено». Интерес и обещание следующего пилота не считать оплатой.

**11. Продажа и развитие**

Гипотеза монетизации: фиксированная плата организатора за событие; подписка при регулярном использовании. Проверять цену разговором о конкретном следующем событии и предложением оплачиваемого пилота после готовности. Не считать доходом депозиты гостей и не строить доход на их неявке.

Для крупного организатора предложить последовательность: одна сессия → серия мероприятий → дополнительные роли/отчёты/брендирование → интеграция с выбранной системой. Массовые потоки требуют отдельного нагрузочного теста; число сотрудников, входов и пользователей пока не проверено.

Ближайшее продуктовое действие: зафиксировать со знакомым организатором конкретную сессию, текущий процесс возврата и готовность трёх гостей пройти тест. Параллельно первой технической задачей сделать сквозной депозит → check-in → возврат. Это даст материал для честного демо и основание решать, стоит ли расширять AttendBack.
